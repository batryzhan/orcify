# CLAUDE.md — Архитектурный гайд и инструкции для AI-агента (Проект "Orcify")

## 1. Описание проекта и научная цель

**Orcify** — это научно-исследовательский проект (разрабатываемый для олимпиад и технических конкурсов), направленный на интеллектуальную автоматизацию бизнес-процессов с приоритетом на **приватность данных (Data Privacy)** и **локальное исполнение (Local-First Execution)**.

### Научная гипотеза и цель
Доказать, что компактная локальная языковая модель (**Gemma 4**) способна эффективно оркестрировать сложные мультишаговые бизнес-процессы через **Model Context Protocol (MCP)** с минимальной задержкой (Latency) и нулевой утечкой чувствительных данных во внешние облачные LLM API. Архитектура демонстрирует, что 4B-модель при строгой декомпозиции контекста и детерминированной валидации обеспечивает высокую точность Tool Calling при низком потреблении вычислительных ресурсов.

## 2. Стек технологий

### Backend & AI
* **Язык и фреймворк:** Python 3.11+, `FastAPI` (асинхронный REST API + стриминг событий).
* **Валидация и типизация:** `Pydantic v2` (строгая типизация всех входов, выходов и контрактов LLM).
* **Локальный инференс LLM:** Unsloth Studio (`unsloth/gemma-4-E4B-it-GGUF`, квант `UD-Q4_K_XL`, контекст 8192) через OpenAI-совместимый API `http://127.0.0.1:8888/v1` (ключ в `backend/.env`, переменные `ORCIFY_LLM_*`). Structured Outputs — через `response_format: json_schema` (strict).
* **Протокол интеграций:** `mcp-python-sdk` (Model Context Protocol для связи с инструментами).
* **Генерация документов:** `docxtpl` (шаблонизация `.docx` по принципу Deterministic Core).
* **Локальная аналитика и парсинг:** `pandas`, `pdfplumber` / `pypdf` (обработка локальных CSV и PDF без отправки в сеть).

### Frontend
* **Сборка и фреймворк:** `Vite.js`, `React 18+`, `TypeScript` (strict mode).
* **Стилизация:** `TailwindCSS`.
* **Асинхронная коммуникация:** Нативный `EventSource` / кастомный хук `useSSE` для приема Server-Sent Events (SSE).

### MCP-серверы и интеграции
* **n8n MCP:** Запуск и координация автоматизированных воркфлоу.
* **Atlassian MCP:** Управление задачами и тикетами в Jira / документирование в Confluence.
* **Higgsfield MCP:** Генерация видеоконтента по подготовленным сценариям.
* **Local Tools MCP:** Локальный сервер для парсинга PDF, финансового анализа CSV и рендеринга документов.

## 3. Архитектурные принципы

### 3.1. Принцип "Deterministic Core" (Детерминированное ядро)
* **СТРОГИЙ ЗАПРЕТ:** Запрещено генерировать текст юридических документов, договоров и контрактов напрямую через свободную генерацию LLM во избежание галлюцинаций в юридических формулировках.
* **LLM как Extractor:** Локальная модель (`gemma4`) выступает исключительно в роли **Экстрактора сущностей (Entity Extractor)**. Она принимает неструктурированный входной поток (переписку из мессенджеров, транскрибацию голосового сообщения, черновик заявки) и возвращает **строгий JSON (Structured Outputs)** с извлеченными реквизитами:
  * `iin` / `bin` (ИИН / БИН, 12 цифр)
  * `amount` и `currency` (Суммы и валюта договора)
  * `start_date` / `end_date` / `deadlines` (Сроки исполнения)
  * `parties` (Наименования сторон, ФИО подписантов, должности, реквизиты)
* **Шаблонизация и валидация:** Бэкенд валидирует полученный JSON через строгие схемы `Pydantic` (проверяя контрольные разряды ИИН/БИН, корректность дат и неотрицательность сумм) и передает проверенный словарь в шаблонизатор `docxtpl` для рендеринга готового файла `.docx`.

### 3.2. Умный роутинг (Smart Routing — двухэтапная обработка)
Несмотря на то что 4B-параметры позволяют модели обрабатывать развернутые системные инструкции, жесткая фильтрация контекста критически важна для минимизации Latency (Time-to-First-Token) и предотвращения ошибок выбора инструмента (Tool Selection Confusion).

1. **Этап 1 — Intent Classification (Классификация намерения):**
   * Входящий запрос пользователя сначала проходит через легковесный классификатор на базе `gemma4`.
   * Модель определяет целевой бизнес-домен задачи: `Legal` (Юриспруденция), `SMM` (Маркетинг и контент), `Finance` (Финансы и отчетность) или `HR` (Кадры).
   * Выход этапа: строго типизированная схема `IntentClassificationResult(domain: DomainEnum, confidence: float, reasoning: str)`.
2. **Этап 2 — Scoped Execution (Исполнение в рамках домена):**
   * В контекстное окно LLM подгружаются **только** те MCP-инструменты и системные промпты, которые относятся к выбранному на Этапе 1 домену:
     * `Legal` -> инструменты `docxtpl` генератора, проверка контрагентов, шаблоны договоров.
     * `SMM` -> инструменты `Higgsfield MCP`, `Atlassian MCP`, `n8n MCP`.
     * `Finance` -> локальный анализатор CSV/PDF, генератор табличных сводок.
     * `HR` -> шаблоны кадровых приказов, трекинг онбординга в `Atlassian MCP`.

### 3.3. Асинхронная обработка и стриминг статусов (SSE)
* Для длительных операций (генерация видео через Higgsfield, парсинг и агрегация больших CSV/PDF отчетов, многошаговые цепочки MCP) запрещено блокировать HTTP-соединение обычным синхронным запросом.
* **Backend (`FastAPI`):** Реализует эндпоинты с `StreamingResponse` (`text/event-stream`), отправляющие структурированные события прогресса в формате JSON:
  * `{"status": "classifying_intent", "progress": 5, "message": "Определение бизнес-домена..."}`
  * `{"status": "anonymizing_pii", "progress": 15, "message": "Маскирование персональных данных..."}`
  * `{"status": "analyzing", "progress": 30, "message": "Извлечение структурированных сущностей..."}`
  * `{"status": "generating_video", "progress": 60, "message": "Генерация видео через Higgsfield MCP..."}`
  * `{"status": "completed", "progress": 100, "result": {...}}`
* **Frontend (`Vite + React`):** Обязан использовать переиспользуемый хук `useSSE` для подписки на поток событий, отображения пошагового прогресс-бара, текущего статуса и плавной обработки обрывов соединения.

### 3.4. MCP Integration Layer (`MCPServerManager`)
* Все взаимодействия с внешними и локальными MCP-серверами инкапсулируются в едином классе-оркестраторе `MCPServerManager`.
* **Динамическое подключение и реестр:** Менеджер поддерживает регистрацию, инициализацию сессий, health-check и фильтрацию инструментов по тегам доменов (`Legal`, `SMM`, `Finance`, `HR`) для серверов `n8n`, `Atlassian`, `Higgsfield` и локальных утилит.
* **Graceful Degradation (Отказоустойчивая деградация):** При вызове любого MCP-сервера обязательна обработка тайм-аутов и ошибок недоступности. Если внешний сервер недоступен, система не должна падать с `500 Internal Server Error`:
  * *Пример для Higgsfield:* Если MCP-сервер генерации видео недоступен или вернул ошибку, `MCPServerManager` перехватывает исключение, возвращает флаг `degraded=True`, а агент автоматически формирует подробный **текстовый сценарий с раскадровкой (storyboard)** и прикрепляет его к задаче в Atlassian.
  * *Пример для Atlassian/n8n:* Сохранение payload задачи в локальную очередь отложенной синхронизации и выдача пользователю готового артефакта в UI.

### 3.5. Безопасность и Приватность (Privacy-by-Design)
* **Local Anonymizer (Локальная анонимизация PII):** Перед передачей любых данных во внешние (облачные) MCP-серверы (например, `Higgsfield` или внешний инстанс `n8n` / `Atlassian`) текст в обязательном порядке проходит через локальный пайплайн `LocalAnonymizer`.
  * Скрипт находит и заменяет чувствительные сущности (PII / коммерческую тайну: ФИО, ИИН, БИН, телефоны, email, физические адреса, названия компаний) на детерминированные токены-плейсхолдеры: `[PERSON_1]`, `[COMPANY_1]`, `[IIN_1]`, `[ADDRESS_1]`.
  * Таблица соответствия (`mapping_table`) хранится строго в оперативной памяти (in-memory) в рамках текущей сессии и уничтожается после завершения запроса. При необходимости де-анонимизации ответа на стороне клиента/бэкенда токены заменяются обратно локально.
* **Безопасное логирование (Zero-PII Logging):** Категорически запрещено логировать сырые тексты пользовательских запросов, содержимое PDF/CSV файлов или извлеченные персональные данные в стандартный вывод или файлы логов. Логируются только `session_id`, `request_id`, SHA-256 хэши артефактов, выбранный домен, тайминги (`latency_ms`) и статусы выполнения этапов.

## 5. Инструкции и правила для AI-агента (Claude Code)

При написании, рефакторинге или генерации любого кода в рамках репозитория **Orcify** неукоснительно соблюдай следующие правила:

1. **Строгая типизация и валидация (Type Safety First):**
   * На бэкенде используй `Pydantic v2` модели для **всех** входных запросов, ответов API, событий SSE, конфигураций и аргументов инструментов. Использование нетипизированных `dict[str, Any]` вместо явной схемы запрещено.
   * На фронтенде используй строгие `TypeScript` интерфейсы (без `any`), зеркалирующие Pydantic-схемы бэкенда.

2. **Только Structured Outputs при работе с LLM:**
   * При каждом обращении к локальной модели (`gemma4`) через `LLMClient.structured()` передавай целевую Pydantic-модель: её JSON Schema уходит в `response_format={"type": "json_schema", "json_schema": {"strict": true, "schema": Model.model_json_schema()}}`, а ответ валидируется `Model.model_validate_json()`.
   * Никогда не парси ответы LLM регулярными выражениями из свободного текста, если требуется извлечение данных или классификация.

3. **Запрет на хардкод промптов:**
   * Никогда не пиши системные промпты или крупные инструкции внутри `.py` файлов.
   * Все промпты должны храниться в директории `/backend/prompts/` в виде отдельных файлов и загружаться через единый загрузчик промптов.

4. **Регистрация MCP-серверов через `MCPServerManager`:**
   * При добавлении любого нового MCP-сервера или инструмента обязательно регистрируй его в `/backend/app/mcp/manager.py` с указанием:
     * домена (`DomainEnum.LEGAL`, `DomainEnum.SMM`, `DomainEnum.FINANCE`, `DomainEnum.HR`),
     * флага `is_external: bool` (если `True`, вызов обязан автоматически проходить через `LocalAnonymizer`),
     * стратегии `fallback_handler` на случай недоступности сервера.

5. **Соблюдение Deterministic Core и Privacy:**
   * Никогда не создавай эндпоинты или функции, где LLM напрямую генерирует финальный текст договора. Только цепочка: `Unstructured Text -> LLM Extractor (JSON) -> Pydantic Validation -> docxtpl Render (.docx)`.
   * Проверяй, что в вызовах `logger.info()` / `logger.error()` отсутствуют поля с пользовательским текстом, ФИО, ИИН/БИН или суммами — логируй только `session_id`, `payload_hash` и метрики времени.

## 6. Сквозные сценарии (MVP Pipelines)

Ниже описаны три эталонных сквозных сценария MVP, которые должны работать безотказно и демонстрировать научную новизну проекта на защите:

### Сценарий А: Legal — Автоматическая генерация контракта из неструктурированного запроса
1. **Вход:** Пользователь отправляет сырой текст (например, скопированную переписку с клиентом в WhatsApp/Telegram с обсуждением условий сделки и реквизитами).
2. **Этап 1 (Smart Routing):** `gemma4` классифицирует запрос в домен `Legal` (SSE: `{"status": "classifying_intent", "progress": 15}`).
3. **Этап 2 (Extraction):** В контекст подгружается схема `ContractEntitiesSchema`. Модель извлекает сущности в строгий JSON: `client_name`, `bin_iin`, `contract_amount`, `currency`, `deadline_date`, `scope_of_work` (SSE: `{"status": "extracting_entities", "progress": 50}`).
4. **Этап 3 (Deterministic Core):** Бэкенд валидирует JSON через Pydantic (проверка формата 12-значного ИИН/БИН и дат) и передает данные в `docxtpl`, заполняя шаблон `/backend/templates/service_contract_kz.docx` (SSE: `{"status": "rendering_docx", "progress": 85}`).
5. **Выход:** Пользователь получает ссылку на скачивание готового юридически выверенного `.docx` контракта (SSE: `{"status": "completed", "progress": 100}`). Ни один байт данных не покинул локальный контур.

### Сценарий Б: SMM — Маркетинговый пайплайн с внешней генерацией и защитой приватности
1. **Вход:** Запрос на создание рекламного видеоролика для продукта компании с упоминанием внутренних имен или клиентских кейсов.
2. **Этап 1 (Smart Routing):** `gemma4` определяет домен `SMM` и подключает только инструменты `Higgsfield MCP` и `Atlassian MCP` (SSE: `{"status": "routing_smm", "progress": 10}`).
3. **Этап 2 (Script & Anonymization):** Локальная LLM формирует структуру сценария и раскадровку. Перед вызовом внешнего облачного MCP-сервера `LocalAnonymizer` заменяет все PII и названия брендов/персон на плейсхолдеры `[PERSON_1]`, `[COMPANY_1]` (SSE: `{"status": "anonymizing_pii", "progress": 25}`).
4. **Этап 3 (Higgsfield MCP + Graceful Degradation):**
   * Вызывается `Higgsfield MCP` для генерации видео (SSE: `{"status": "generating_video", "progress": 55}`).
   * *Если сервер доступен:* возвращается URL/файл сгенерированного видео.
   * *Если сервер недоступен (Fallback):* `MCPServerManager` перехватывает ошибку и формирует детализированный текстовый storyboard-сценарий для ручного продакшена.
5. **Этап 4 (Atlassian MCP):** Автоматически создается задача в Jira через `Atlassian MCP` с прикрепленным видео (или fallback-сценарием), де-анонимизированным локально для внутреннего трекера (SSE: `{"status": "creating_jira_issue", "progress": 85}` -> `{"status": "completed", "progress": 100}`).

### Сценарий В: Finance — Локальный финансовый анализ CSV и генерация отчета
1. **Вход:** Пользователь загружает CSV-выгрузку банковских транзакций или финансовой отчетности.
2. **Этап 1 (Smart Routing):** `gemma4` классифицирует задачу в домен `Finance` и активирует только `local_finance_server` MCP (SSE: `{"status": "routing_finance", "progress": 15}`).
3. **Этап 2 (Local Data Processing):** Локальный MCP-инструмент на базе `pandas` рассчитывает детерминированные агрегаты (выручка, расходы по категориям, кассовые разрывы, топ контрагентов, аномалии) без передачи сырых строк таблицы в промпт LLM (SSE: `{"status": "analyzing_csv", "progress": 50}`).
4. **Этап 3 (Structured Executive Summary):** `gemma4` получает только агрегированные статистические метрики и генерирует структурированное аналитическое резюме (`FinanceReportSchema`: выводы, риски, рекомендации) (SSE: `{"status": "generating_report", "progress": 85}`).
5. **Выход:** Фронтенд отображает интерактивную сводку и отдает готовый локальный отчет (SSE: `{"status": "completed", "progress": 100}`).

## 7. Научные метрики и эксперименты (Папка `/docs`)

При разработке функционала необходимо поддерживать сбор телеметрии (без PII) для раздела `/docs/metrics.md`:
* **Routing Overhead & Latency:** Сравнение времени ответа `gemma4` со Smart Routing (узкий набор MCP-инструментов домена) против подачи всех MCP-инструментов сразу.
* **Tool Calling Accuracy:** Процент валидных JSON-ответов и корректных вызовов MCP-инструментов с первой попытки (Zero-Shot Tool Call Success Rate).
* **PII Leakage Rate:** Подтверждение `0%` утечки чувствительных сущностей во внешние MCP благодаря фильтру `LocalAnonymizer`.
